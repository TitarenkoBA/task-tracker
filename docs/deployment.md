# Публикация на GitHub Pages

Приложение публикуется автоматически: каждый push в ветку `main` проверяется, собирается
и выкладывается на GitHub Pages. Настроено в `.github/workflows/deploy.yml`.

## Что происходит автоматически

| Событие | Что делает GitHub Actions |
| --- | --- |
| Pull request в `main` | Проверка форматирования, тесты, сборка. Ничего не публикуется — это проверка перед слиянием |
| Push (или слияние PR) в `main` | То же самое + публикация на GitHub Pages |
| Вручную (вкладка **Actions** → **Deploy to GitHub Pages** → **Run workflow**) | Публикация текущего `main` |

Если тесты или форматирование не прошли — сайт **не обновится**, останется прошлая рабочая версия.

## Первая настройка (один раз)

### 1. Создать репозиторий на GitHub

Откройте <https://github.com/new>, задайте имя (например, `task-tracker`) и создайте **пустой** репозиторий —
без README, .gitignore и лицензии (они уже есть в проекте).

> GitHub Pages бесплатен для **публичных** репозиториев. Для приватных нужен платный тариф
> (GitHub Pro / Team). Данные пользователей в репозиторий не попадают — они хранятся в браузере.

### 2. Отправить код

В папке проекта (подставьте своё имя пользователя и имя репозитория):

```bash
git remote add origin https://github.com/<user>/task-tracker.git
git push -u origin main
```

### 3. Включить GitHub Pages

В репозитории: **Settings → Pages → Build and deployment → Source: GitHub Actions**.

Затем откройте вкладку **Actions**: первый запуск мог упасть, если Pages ещё не был включён, —
нажмите **Re-run all jobs**. Через 1–2 минуты сайт будет доступен по адресу:

```
https://<user>.github.io/task-tracker/
```

Ссылка также появляется на странице запуска в Actions и в **Settings → Pages**.

## Как это устроено

1. **Адрес в подпапке.** Сайт живёт в `/<имя-репозитория>/`, поэтому сборка запускается с
   `--base-href /<имя-репозитория>/` — имя берётся автоматически. Если репозиторий называется
   `<user>.github.io`, используется `/`.
2. **Прямые ссылки.** GitHub Pages не умеет отдавать `index.html` для любых адресов. Поэтому при сборке
   создаётся копия `404.html`: ссылка `/task-tracker/browse/WEB-1` и обновление страницы работают.
3. **PWA и обновления.** Service Worker работает в пределах `/<имя-репозитория>/`. После публикации
   новой версии пользователи увидят плашку «Доступна новая версия → Обновить».
4. **Данные пользователей** хранятся в браузере и привязаны к адресу сайта. Если адрес сменится
   (переименование репозитория, свой домен), данные останутся на старом адресе — заранее сделайте экспорт.

## Свой домен

1. **Settings → Pages → Custom domain** — укажите домен и настройте DNS по
   [инструкции GitHub](https://docs.github.com/pages/configuring-a-custom-domain-for-your-github-pages-site).
2. **Settings → Secrets and variables → Actions → Variables → New repository variable**:
   `BASE_HREF` = `/`. Без этого приложение будет искать файлы в несуществующей подпапке.
3. Запустите workflow вручную или сделайте любой push в `main`.

## Если что-то пошло не так

| Симптом | Причина и решение |
| --- | --- |
| Красный крестик в Actions на шаге **Check formatting** | Запустите `npm run format` и закоммитьте |
| Падает **Unit tests** | Запустите `npm run test:ci` локально, лог ошибки — в Actions |
| Падает **Deploy** с ошибкой про Pages | Не включён Pages с источником **GitHub Actions** (шаг 3) |
| Белый экран, в консоли 404 на `.js`-файлы | Неверный base href: проверьте имя репозитория или переменную `BASE_HREF` |
| После публикации видна старая версия | Кэш Service Worker: дождитесь плашки «Обновить» или обновите страницу дважды |
| `npm ci` падает: lock-файл не совпадает | Выполните `npm install` локально и закоммитьте `package-lock.json` |
